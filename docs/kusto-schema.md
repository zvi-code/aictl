# Kusto schema

Generated by `aictl.kusto.schema.render_markdown()` from `storage._SCHEMA_SQL`; do not edit by hand (`aictl db schema --markdown` prints it, and a test compares this file to it).

One Kusto database (`kusto_database`, default `aictl`) holds every table. Each table keeps its SQLite name and columns and gains the system columns `rowid:long` (assigned by the connection; the value of an `INTEGER PRIMARY KEY` column), `_v:datetime` (when this version was written) and `_deleted:bool`. Rows are versions: a read keeps the newest `_v` per key and drops deleted rows. The key is the PRIMARY KEY, else a UNIQUE constraint, else `rowid`; unique indexes are the extra conflict sets SQLite's `OR IGNORE` and `ON CONFLICT` honour.

Nothing is per project at the database level: the SQLite split into one file per repository existed for SQLite's write lock, which Kusto does not have. Scope comes from the `session_id` and `project_path` columns. The same description is in the database itself, as the table `aictl_information_schema` (one row per column), rewritten on every start.
